# Iteration 3：用户端选品 + 纯人工客服实时双端通讯

**目的**

发起一次咨询的前提是用户先知道"我要问哪个商户的哪个商品"。本迭代打通"浏览商品 → 选中 → 发起会话 → 双端实时通讯 → 历史可查"这条纯人工路径，AI还未接入，所有对话默认走人工客服。"浏览门槛越低越好"这一原则只适用于商品浏览，不延伸到发起会话——发起会话需要一个可核实的身份。

**选型**

| 项 | 选择 | 理由 |
|---|---|---|
| 商品浏览 | 公开只读接口，不需要登录即可浏览全部商户的商品 | 客服场景典型路径是"先看东西，再决定要不要问"，浏览门槛越低越好 |
| **发起咨询的身份要求** | **要求用户已登录，游客只能浏览商品、不能发起会话** | **会话和历史消息需要长期归属，临时身份会导致下次回来找不回历史对话，不如直接要求登录** |
| 发起咨询 | 商品详情页"咨询"按钮，携带该商品及所属商户信息建立会话 | 把"选品"和"发起会话"显式串联，不让前端凭空传一个不知道对应哪个商品的请求 |
| **重复咨询的会话归并** | **同一用户对同一商户同一商品重复发起咨询时，复用已有的未结束会话，不重复新建** | **避免同一段咨询关系被拆成多条互不相关的历史记录，查询体验碎片化** |
| 实时通信 | WebSocket，用户端点和商户端点各自维护连接池 | 客服场景对实时性要求高 |
| **实时连接的身份可信度** | **建立连接时要核实"发起方声明的身份"和"其登录凭证"是否一致，商户侧复用迭代2已有的登录凭证机制** | **连接发起方声明的身份是自己填的，不可信；这和迭代2解决的"不能冒充别人操作资源"是同一类风险，实时连接不该是校验的空白地带** |
| 会话与消息 | 会话记录选中的商品，每条消息落库，固定为人工处理模式 | 还没有AI角色概念，所有对话默认人工处理 |
| **会话归属信息的防篡改方式** | **会话一旦建立，归属的商品和商户就固定下来，后续消息里出现的不一致信息不会生效** | **避免一段已建立的咨询关系中途被换绑到别的商品或商户** |
| 消息可靠性策略 | 先落库、再尝试实时转发（而不是先转发、失败了再落库） | 保证商户离线时消息不丢，不需要额外的离线队列/推送机制 |

**关键约束**

1. 商品浏览必须公开可访问，不能被迭代2的商户身份校验波及
2. 会话一旦创建，归属的商品和商户信息不可通过后续消息被更改
3. 商户当前不在线时，用户发送的消息仍必须成功落库，不能因商户离线而报错或丢失；若落库本身失败，必须明确告知发送方"没发出去"，不能让消息悄悄消失
4. 双方都能查询到该会话的完整历史消息
5. 建立实时连接时必须核实声明身份与登录凭证一致，冒充他人身份的连接请求必须被拒绝
6. 历史会话查询，商户和用户两侧都必须校验"请求方是不是在查自己的数据"，不能仅凭传入的一个ID就返回结果

**本次不做**

- AI接入、转人工判定逻辑（这个阶段还没有AI，谈不上"转"人工）
- 消息已读/未读状态、多端同时在线的连接管理
- 消息推送到站外（邮件/短信通知商户）
- 游客（未登录）发起咨询——本迭代要求发起会话前必须完成登录

**验收命令**

**1. 未登录可浏览全部商品**
```bash
curl -s -X GET http://localhost:8080/goods/pageInfo
```
→ 断言：返回全部商户的商品列表，无需任何身份凭证

**2. 用户发起会话**
```bash
# WS连接 ws://localhost:8080/user/chat/{userId}（携带用户登录凭证）
# 发送: {"goodsId": 1, "ctId": 1, "message": "你好"}
```
→ 断言：收到"会话已确认建立"的响应状态，携带新生成的会话标识，服务端记录该会话为人工处理模式

**3. 归属信息不可被后续消息篡改**
```bash
# 同一会话标识下发送: {"sessionId": "上一步的id", "goodsId": 999, "message": "测试篡改"}
```
→ 断言：该会话归属的商品信息仍是最初创建时的值，未被改成999

**4. 商户实时收到并回复**
```bash
# 商户WS连接 ws://localhost:8080/commercialTenant/chat/{ctId}（携带登录凭证）
# 断言：能收到步骤2用户发送的消息推送
# 商户回复: {"sessionId": "...", "message": "您好，有什么可以帮您"}
```
→ 断言：用户端能实时收到商户的回复

**5. 商户离线时消息不丢**
```bash
# 不建立商户WS连接，用户直接发消息
curl -s "http://localhost:8080/sessionLog/getWindowMessage?sessionId=xxx"
```
→ 断言：消息已正常写入，可查询到，不因商户离线而报错

**6. 历史记录双向可查**
```bash
curl -s "http://localhost:8080/session/ctGetLastSessionList?ctId=1" -H "Authorization: token_A"
curl -s "http://localhost:8080/session/userGetLastSessionList?userId=1" -H "Authorization: user_token_1"
```
→ 断言：商户和用户各自都能在自己的会话列表里看到这个会话，且能拉到完整历史消息

**7. 冒充他人身份建立连接必须被拒绝**
```bash
# 用商户A的登录凭证，尝试连接 ws://localhost:8080/commercialTenant/chat/{ctId_B}
```
→ 断言：连接被拒绝，不能以商户B的身份收发消息

**8. 历史查询越权必须被拒绝**
```bash
curl -s "http://localhost:8080/session/ctGetLastSessionList?ctId=2" -H "Authorization: token_A"
```
→ 断言：token_A对应的是商户A（ctId=1），查询ctId=2被拒绝，不返回商户2的会话数据

**9. 重复咨询复用同一会话**
```bash
# 用户对goodsId=1,ctId=1第一次发起会话，得到sessionId_1
# 断开重连，再次对goodsId=1,ctId=1发起会话（不带sessionId）
```
→ 断言：第二次返回的会话标识与sessionId_1相同，未创建新会话
